# Build brief for screen agents (read fully before starting)

Project: ITHC Fleet Operations Platform frontend (Next.js 16 / React 19 / Tailwind 4 / shadcn on @base-ui). Demo mode only: no backend, no real auth. Goal: replace each skeleton page with a working-looking screen that matches the end result described by the spec (`../../Docs/ITHC_FLEET_PLATFORM_SPEC.pdf`, text via `pdftotext -layout`), using realistic mock data. Visual polish is NOT the goal (a separate UI/UX session does that); completeness and correct behaviour are.

IMPORTANT: Next.js here has breaking changes. `AGENTS.md` says to read `node_modules/next/dist/docs/` before writing Next-specific code. Screens are plain client components, so you mostly need React, but check the docs if you use any Next API.

## What already exists (do not rebuild, do not edit)
- `src/config/**` : role/page config. Each page has `requirements[]`, `future[]`, `shell`. READ the config for every page you own: its requirements are your build checklist. NEVER edit requirement text, reorder, add or remove requirements.
- `PAGE_MAP.txt` : every `role/page` key, its `source` (shared base page or `-`), read-only flag, requirement count. Find the keys you own from your assignment.
- `src/screens/registry.ts` : looks up a screen by `"<role>/<page>"` first, then by the page's `source` (e.g. `"operations/orders"`). Register shared screens by SOURCE key so every role that reuses the page gets it; register by role key when a page is role-specific. Screens receive `ScreenProps {role, page, readOnly, editedBy}` (see `src/screens/types.ts`). When `readOnly` is true: show `<ReadOnlyBanner editedBy>` and hide all create/edit/delete actions.
- Shared UI in `src/components/app/`: `PageHeader`, `ReadOnlyBanner`, `KpiCard/KpiGrid`, `StatusBadge/toneFor/prettify`, `DataTable` (search/sort/CSV export/paging), `FormSheet` (slide-over form/detail), `Field/Input/Select/Textarea`, `Tabs`, `useById`. shadcn pieces in `src/components/ui/` (Button, Card, Badge, Sheet, Separator, ScrollArea, Collapsible). lucide-react icons. You may add small components inside your own folder.
- Data layer `src/data/store.ts`: `defineCollection<T>(name, seedFn)` gives `.useAll()` hook, `.save()`, `.saveMany()`, `.remove()`, `.getSync()`, `.nextId()`, persisted in localStorage. Core collections in `src/data/core.ts`: `workers, vehicles, clients, contracts, locations, companies` (+ types in `src/data/entities.ts`, seeds in `src/data/seed/core.ts`). You may READ and `.save()` core collections. Do not edit `entities.ts`/`seed/core.ts`/`store.ts`; if you need extra fields, keep them in your own area collections keyed by core ids.
- `src/lib/money.ts`: money is integer FILS everywhere. Use `formatKD(fils)` (always 3 decimals), `parseKD`, `formatFils`. NEVER use floats for money. `src/lib/dates.ts`: business dates are `"YYYY-MM-DD"` strings; `TODAY = "2026-11-09"` is the demo's fixed today; `addDays, daysBetween, fmtDate, overlaps`. `src/lib/auth.ts`: `useSession()` gives the demo user.

## Rules
1. Only create/edit files inside YOUR area: `src/screens/<area>/**`, `src/data/<area>/**`, `src/services/<area>/**` (optional), and `src/config/status/<area>.ts`. Do NOT touch any other file. If you think a shared file needs a change, do not make it; describe it in your final report.
2. Do NOT import from another area's `src/screens/**` or `src/data/<other-area>/**` (areas are built in parallel; those files may not exist yet). Cross-area numbers must be derived from core collections or from your own area's seeded mock data. Note any resulting inconsistency in your report.
3. Every page you own gets a complete screen: realistic seeded mock data (enough rows to feel real: 15 to 40, plus edge cases such as an expired item, a conflict, a negative margin), list/filters/search, detail view, create/edit forms that actually save to the collection (via `FormSheet`), validation, and the page's specific actions. Behaviour must follow the requirement texts and the spec (e.g. date-ranged assignments with inclusive end dates and overlap detection, contract versions instead of edits, audit entries with a mandatory reason where the spec says so, optimistic-locking `version` check on edit forms, KD with 3 decimals, config-driven rates).
4. The requirements text must NOT appear as page content. The slide-over (built already) shows them. The page shows only the working UI.
5. Layout by role device: desktop roles are dense, tabular, keyboard-friendly. Handover desk is tablet: very large touch targets (min 56px), few fields per step, no small dropdowns, complete a routine handover in about 3 taps per step, camera capture step (use `<input type="file" accept="image/*" capture="environment">`), offline-queue indicator and a toggle that simulates offline so events queue and later sync. Site supervisor and worker are mobile: single column, big buttons.
6. Use logical CSS properties (`ms-*`, `me-*`, `ps-*`, `pe-*`, `text-start`, `text-end`, `start-*`, `end-*`) so RTL can be added later. English only.
7. Screens are client components (`"use client"`), default-exported, named per page, registered in `src/screens/<area>/index.ts` under the correct keys (see assignment). Keep files focused (aim under ~400 lines each; split into sub-components in your folder).
8. Quality gates (run these yourself, repeatedly): `npx tsc --noEmit` and `npx eslint src/screens/<area> src/data/<area> src/config/status/<area>.ts` from the `frontend` folder. Fix every error in your files. Ignore errors in other areas' files (they are being written at the same time). DO NOT run `next build` or `next dev` (parallel builds corrupt `.next`). Do not commit to git. Do not install packages.
9. Built-status honesty (very important). In `src/config/status/<area>.ts` add an entry for EVERY `"<role>/<page>"` key you own (including role pages that reuse your shared source screen): `"ops-role/page": built({ 3: "what is missing", 7: "what is missing" })`. The numbers are 0-based indexes into that exact page's final `requirements` array (as listed in config/PAGE_MAP; for `pick()` pages with `readOnlyBy`, index 0 is the added "Read-only view" requirement). A requirement not listed counts as BUILT, so list every requirement that is not fully implemented on the screen, with a short note of what is missing. Do not list a requirement as built if it is only a label with no behaviour. Never claim verification; the user ticks the checkbox, not you. If you skip a whole page, leave it out of the status file entirely (it then shows as Pending).
10. Final report (keep under 300 words): pages built, pages skipped or partly built and why, cross-area inconsistencies, shared-file changes you want, and the result of tsc and eslint for your area.
